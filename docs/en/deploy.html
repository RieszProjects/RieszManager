Deployment

This page is the full deployment reference: architecture, configuration, HTTPS, account security, push notifications, upgrades, backups, and troubleshooting. If you just want to get it running first, see Quickstart; for day-to-day usage once deployed, see the User Guide.

Components and requirements

Riesz Manager consists of a runner on the host and three Docker containers:

ComponentWhere it runsDescription
runnerHost (systemd user service)Reads ~/.claude, browses the workspace, and spawns and drives claude processes
backendDockerDjango (ASGI/uvicorn); handles sign-in, two-factor authentication, API and WebSocket proxying, and push notifications
frontendDockerPre-built static frontend served by nginx
gatewayDockernginx gateway listening on RIESZ_BIND:RIESZ_PORT (127.0.0.1:18573 by default)

The runner and the backend container must run as the same user (same UID/GID): the container reaches the runner's Unix socket through a bind-mounted directory, and the socket is only readable and writable by that user.

The host machine needs:

  • Linux with systemd: systemd manages the runner's user service.
  • Claude Code installed and signed in: running claude as the target user should work normally.
  • Python ≥ 3.10: used by the runner.
  • Docker Engine and Docker Compose v2: the user running rieszctl must be able to run docker (add the user to the docker group and log back in).
  • A TLS terminator: Cloudflare Tunnel, Caddy, nginx with a certificate, or similar. Do not expose the gateway port directly to the public internet.

Get the code

Clone the repository and run init to generate the initial configuration file:

git clone https://github.com/RieszProjects/RieszManager.git RieszManager
cd RieszManager
./rieszctl init

./rieszctl init creates .env (mode 600) from .env.example and fills in:

  • RIESZ_SECRET_KEY and RUNNER_TOKEN: randomly generated secrets;
  • RIESZ_PASSWORD: a random temporary password, printed to the terminal;
  • RIESZ_UID / RIESZ_GID: the current user's UID and GID;
  • RUNNER_SOCKET_DIR: ~/.local/state/riesz-manager/run;
  • WORKSPACE_ROOT: defaults to the current user's home directory, or pass WORKSPACE_ROOT=/path ./rieszctl init to set it at init time.

Configure .env

.env is read by Docker Compose, the backend container, and the host runner. Open .env and review at least these settings:

VariableDescription
WORKSPACE_ROOTWorkspace root directory; each top-level subfolder under it is treated as a project
RIESZ_PUBLIC_ORIGINPublic URL, e.g. https://claude.example.com (used for CSRF, WebSocket origin checks, and secure cookies)
RIESZ_USERNAME / RIESZ_PASSWORDSign-in credentials; switching to RIESZ_PASSWORD_HASH is recommended—see Account and two-factor authentication
RIESZ_PORT / RIESZ_BINDGateway listen address; listens only on 127.0.0.1:18573 by default
RIESZ_TRUST_CF_HEADERSet to true when behind Cloudflare Tunnel so rate limiting uses the real client IP
RUNNER_DEFAULT_PERMISSION_MODEDefault permission mode for new sessions; see Permission modes and models
RUNNER_ALLOW_BYPASSWhether sessions can be switched to “Bypass permissions” (跳过权限) mode from the web UI
RUNNER_CHROMEWhether web sessions connect to Claude in Chrome: auto (follows your /chrome default from the terminal), on, or off
OPENAI_API_KEYOptional; enables server-side voice transcription
RIESZ_VAPID_PRIVATE_KEYOptional; signing key for push notifications. If left empty, one is generated on first use and saved to data/backend/vapid_private.pem

See the Environment variable reference at the end of this page for the complete list.

Values in .env that contain $ (such as a password hash pbkdf2_sha256$...) must be wrapped in single quotes, or they will be expanded as variables.

Install the runner

As the host user that will run Claude Code, run:

./rieszctl runner install

This command does three things:

  1. Creates a Python virtual environment in runner/.venv and installs dependencies;
  2. Writes ~/.config/systemd/user/riesz-runner.service and starts the service;
  3. Attempts loginctl enable-linger $USER so the user service keeps running after you log out of SSH or reboot the host (if it lacks permission, it will print the sudo command for you to run manually).

By default, the runner launches claude through a login shell ($SHELL -lc), so Bash commands inside a session see the same environment variables as your terminal. Set RUNNER_LOGIN_SHELL=false in .env if you do not want this.

Common runner commands:

./rieszctl runner status
./rieszctl runner logs
./rieszctl runner reload      # Apply new code or .env changes: reloads once all managed sessions are idle
./rieszctl runner restart     # Restart immediately: interrupts any session currently running a turn

reload waits until every Claude session managed by the runner is idle (no turn in progress, no pending permission prompt, no queued messages, and no background commands, subagents or monitors still running), then stops those idle processes and reloads itself; session history lives on disk and resumes automatically on the next message. restart takes effect immediately and interrupts active turns, so it is normally only needed if the runner is stuck. Other subcommands include start, stop, uninstall, and run (run in the foreground).

Start the containers

Build and start the three containers, then check overall status:

./rieszctl up
./rieszctl status

./rieszctl status checks the runner socket, container status, and the gateway health endpoint at http://127.0.0.1:$RIESZ_PORT/api/healthz. The backend's SQLite database is stored under data/backend/ in the repository and holds login records, two-factor secrets, archive and ordering state, quick phrases, and push subscriptions.

Day-to-day container commands:

./rieszctl restart            # Restart containers after changing container-related .env settings
./rieszctl up                 # Rebuild and start after pulling new code
./rieszctl down               # Stop containers
./rieszctl logs               # Tail logs for all containers, or pass a service name, e.g. ./rieszctl logs backend

Configure HTTPS

The gateway container speaks plain HTTP and listens on 127.0.0.1:18573 by default. To serve it externally, put a TLS terminator in front of it. Here are three common setups.

Cloudflare Tunnel (recommended)

  1. In the Cloudflare Zero Trust dashboard, go to Networks → Tunnels, create (or pick) a tunnel, and follow the instructions to install the cloudflared connector on the host.
  2. Under the tunnel's Public Hostname tab, add a route: set Subdomain / Domain to your domain, choose HTTP as the Service, and set the URL to localhost:18573 (matching RIESZ_PORT).
  3. In .env, set RIESZ_PUBLIC_ORIGIN=https://your-domain and RIESZ_TRUST_CF_HEADER=true, then run ./rieszctl restart.

WebSockets pass through automatically without extra configuration. If you want an extra gate in front of the login page, you can attach a Cloudflare Access policy to the domain.

Caddy

Add to your Caddyfile:

claude.example.com {
    reverse_proxy 127.0.0.1:18573
}

Caddy obtains a certificate and sets X-Forwarded-Proto automatically. Remember to set RIESZ_PUBLIC_ORIGIN in .env to https://claude.example.com and restart the containers.

Existing nginx

If the host already runs nginx with a certificate, add a site block like the following (note the Upgrade and Connection headers required for WebSockets and the long read timeout):

server {
    listen 443 ssl http2;
    server_name claude.example.com;
    ssl_certificate     /path/fullchain.pem;
    ssl_certificate_key /path/privkey.pem;
    client_max_body_size 210m;
    location / {
        proxy_pass http://127.0.0.1:18573;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 1d;
    }
}

Account and two-factor authentication

  • Change the password: run ./rieszctl hash-password on the host, enter the new password when prompted, copy the printed RIESZ_PASSWORD_HASH='...' line into .env, remove or clear RIESZ_PASSWORD, and run ./rieszctl restart. When RIESZ_PASSWORD_HASH is set, it takes precedence over the plaintext RIESZ_PASSWORD.
  • Enable two-factor authentication: after signing in to the web UI, open “Settings” (设置) → “Security” (安全) → “Start setup” (开始设置), scan the QR code with an authenticator app on your phone, enter the 6-digit code, and store the 8 single-use recovery codes shown on the page in a safe place. See Settings for details.
  • Require two-factor authentication: set RIESZ_REQUIRE_TOTP=true in .env. Once enabled, a signed-in user can only access the settings page until an authenticator is bound.
  • Lost authenticator: sign in using one of the recovery codes you saved earlier; if those are also lost, run ./rieszctl reset-totp on the host to disable two-factor authentication directly.
  • Sign out all devices: use “Settings” (设置) → “Devices” (设备), or run ./rieszctl revoke-sessions on the host.

The sign-in endpoint rate-limits failed attempts: a single client IP is temporarily locked out after RIESZ_LOGIN_MAX_FAILURES consecutive failures within RIESZ_LOGIN_LOCKOUT_MINUTES minutes; if total failures across all IPs reach RIESZ_LOGIN_MAX_FAILURES_GLOBAL, sign-in is throttled site-wide.

Push notifications

Riesz Manager uses standard browser Web Push: when you enable notifications in a browser, that browser vendor's push service (Google FCM for Chrome, Mozilla for Firefox, Apple for Safari/iPhone) assigns a push endpoint, and the backend container sends end-to-end encrypted payloads directly to that endpoint whenever a notification is needed. No third-party account or API key is required, nothing goes through any server run by the Riesz Manager authors, and each deployment uses its own generated keys.

What the deployment needs:

  • HTTPS: browsers only expose Web Push on HTTPS origins (or 127.0.0.1); RIESZ_PUBLIC_ORIGIN is used as the VAPID contact URI.
  • Outbound internet access: the backend container runs a background task that listens for runner events and needs outbound HTTPS access to reach each browser vendor's push service.
  • Signing key (VAPID): RIESZ_VAPID_PRIVATE_KEY in .env can be left empty. On first use of push notifications, a key is generated automatically and saved to data/backend/vapid_private.pem (owner-readable only). If this key is later replaced or lost, all existing device subscriptions stop working and push will need to be toggled back on in “Settings” (设置) on each device.
  • Client requirements: Android phones need connectivity to Google services; iPhones require iOS 16.4 or later, and the web app must first be added to the Home Screen (“Add to Home Screen”) and opened from that icon before it can subscribe.

See User Guide: Push notifications for how to enable push on each device and when notifications are sent.

Balances of other services

The doll's panel can show account balances of other AI services; the types deepseek, openrouter and novelai are supported. To use it, create balances.json in the runner's state directory (by default ~/.local/state/riesz-manager/balances.json; set RUNNER_BALANCES_FILE to use another path) listing each service and a command that prints its API key:

{
  "providers": [
    {"type": "deepseek", "keyCommand": "cat ~/.config/keys/deepseek"},
    {"type": "openrouter", "keyCommand": "printenv OPENROUTER_API_KEY"},
    {"type": "novelai", "keyCommand": "pass show novelai"}
  ]
}
  • keyCommand runs in the runner user's login shell; the last non-empty line of its output is used as the key. It can read a file or an environment variable, or call a password manager.
  • Keys are fetched for each check and dropped afterwards; they are never logged or sent to the browser, which only receives the balances.
  • Balances are checked at most every 15 minutes; “Refresh usage” (刷新用量) in the doll's context menu checks again right away (at most once a minute).
  • Changes to the file apply on the next check without restarting the runner. An optional "label" field changes the name shown.

The file describes how your keys are obtained, so make it readable only by you (chmod 600).

Upgrading

After pulling new code, update the runner and the containers in order:

git pull
./rieszctl runner install     # Update runner dependencies; reloads gracefully if the service is already running (without interrupting active sessions)
./rieszctl up                 # Rebuild and start containers

Backup

Only two things belong to Riesz Manager itself and need backing up:

  • .env: all configuration and secrets;
  • data/backend/: the backend SQLite database (two-factor secrets, login sessions, and device push subscriptions) and the auto-generated vapid_private.pem push signing key. If that key is lost, push notifications will need to be re-enabled in Settings on each device.

Conversation logs themselves are stored by Claude Code under ~/.claude/projects/; attachments uploaded from the web UI are stored under ~/.local/state/riesz-manager/uploads/ (files older than 30 days are cleaned up automatically).

Security notes

Anyone who can sign in to Riesz Manager can ask Claude to run commands and read or write any file accessible to the host user. Always use a strong password and enable two-factor authentication.

  • Bind the gateway to localhost: the gateway listens only on 127.0.0.1 by default. Do not change RIESZ_BIND to 0.0.0.0 and expose it directly to the internet; always put a TLS terminator in front of it.
  • When to trust the Cloudflare IP header: only set RIESZ_TRUST_CF_HEADER=true when traffic genuinely arrives through Cloudflare and the gateway is bound to localhost; otherwise a client could spoof the CF-Connecting-IP header and bypass per-IP login rate limiting.
  • Runner socket isolation: the runner listens only on a Unix socket (directory mode 0750, socket mode 0660) and verifies RUNNER_TOKEN on every request.
  • Read-only project files and path confinement: the project file browser in the web UI serves files read-only, resolves symlinks, and strictly confines paths to the current project directory; raw file downloads and views carry Content-Security-Policy: sandbox so scripts cannot execute under the site's origin.
  • Sandboxed HTML preview: rendered HTML previews load through /api/view/<token>/<path>. The token is a signed, read-only credential scoped to a single project and expires after one hour; responses carry Content-Security-Policy: sandbox (without allow-same-origin), so scripts on the page run in an opaque origin with no access to the site's cookies, local storage, or APIs. Because a previewed page can still load external network resources, the most it can read and exfiltrate is other files within that same project directory.
  • Encrypted push payloads: Web Push payloads are end-to-end encrypted with keys generated by the browser, so the browser vendor's push service cannot read notification contents in transit.
  • Plan usage queries: the plan usage shown by the Riesz doll comes from the runner periodically running claude -p /usage locally. This is a built-in Claude Code command: it does not call the model, consumes no quota, and leaves no session history.

Troubleshooting

SymptomWhat to check
Page says “Host runner disconnected” (宿主机运行器未连接)Run ./rieszctl runner status to see if the service is running; check that RUNNER_SOCKET_DIR in .env is an absolute path matching the runner; verify that RIESZ_UID/RIESZ_GID match the host user running the runner.
Signed out immediately / CSRF error on loginRIESZ_PUBLIC_ORIGIN must match the URL in the browser's address bar exactly (scheme + host + port, no trailing slash). Run ./rieszctl restart after editing.
WebSocket fails to connectCheck that your reverse proxy forwards the Upgrade and Connection headers; see the Existing nginx example above.
New sessions fail to startRun ./rieszctl runner logs to see the error; in a terminal as the same host user, run claude -p "hi" to confirm Claude Code is signed in and responds normally.
Voice button is unavailableBrowsers only allow microphone access on HTTPS (or localhost); also, if OPENAI_API_KEY is not set, voice input relies on the browser's built-in speech recognition.

Uninstalling

Stop the containers and remove the runner user service from the host:

./rieszctl down
./rieszctl runner uninstall

If you no longer want to keep configuration or runtime data, you can also delete:

  • data/ and .env in the repository directory (or remove the repository directory altogether);
  • ~/.local/state/riesz-manager (stores uploaded attachments, input history, and other runner state).

All conversation logs live under ~/.claude/projects/ and belong to Claude Code itself; uninstalling Riesz Manager does not touch them.
